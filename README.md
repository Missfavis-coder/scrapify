# Technical Design Document
## Web Workflow Automation Engine (working title)

Companion to PRD.md. Covers architecture, stack, schema, API design, and current build status.

---

## 1. Architecture Overview

Monorepo, pnpm workspaces (workspace config not yet finalized at repo root — backend is currently being developed standalone at `replay/backend`, run directly with local scripts rather than `pnpm --filter`).

Planned structure:

```
apps/
  web/                 # Next.js frontend
  api/                 # Express backend (currently at replay/backend)
services/
  data/                # Python workflow/discovery-support processing
actor/                 # Apify Actor entry point (Actor.main(), INPUT_SCHEMA.json)
packages/
  workflow-schema/     # Shared workflow definitions
  types/                # Shared TypeScript types
docs/
```

Data flow:

```
Task input (Frontend)
   → Discovery (Playwright, backend/automation)
   → Workflow graph (structured representation)
   → Compilation (workflow graph → executable Playwright steps)
   → Execution (runs the compiled steps)
   → Structured results (Dataset / results table)
   → (stretch) Self-healing on step failure
   → (stretch) Scheduled re-run via Apify Schedules
```

## 3. Backend Folder Structure (`apps/api`, currently `replay/backend`)

```
src/

  app.ts                    # Express app definition (no listen call, exportable for testing)

  config/
    env.ts                  # Loads & validates env vars via Zod, fails fast on missing/invalid

  db/
    client.ts               # Neon connection + Drizzle client
    schema.ts                # Drizzle table definitions
    migrations/               # Auto-generated by drizzle-kit

  routes/
    workflows.routes.ts
    runs.routes.ts
    health.routes.ts

  controllers/
    workflows.controller.ts
    runs.controller.ts

  services/
    discovery.service.ts     # Orchestrates Playwright discovery
    compiler.service.ts      # Converts workflow graph → executable steps
    execution.service.ts     # Runs compiled workflow, collects results
    workflow.service.ts      # CRUD for saved workflows
    apify.service.ts         # Apify API calls (trigger runs, manage Schedules)

  automation/
    browser.ts               # Playwright browser/context lifecycle
    discover.ts               # Element discovery logic
    actions.ts                # Reusable action primitives (click, type, extract, navigate)
    test-browser.ts          # Standalone smoke-test script, isolated from the rest of the app

  schemas/
    task.schema.ts            # Zod validation for incoming task/URL input
    workflow.schema.ts        # Zod validation for workflow structure

  middleware/
    errorHandler.ts
    validateRequest.ts

  utils/
    logger.ts

.env.example
package.json
tsconfig.json
drizzle.config.ts
```

Design rationale:
- routes → controllers → services separates HTTP concerns from logic, so services can eventually be called by the Actor entry point or the Python data service without depending on Express.
- `automation/` (raw Playwright primitives) is separate from `services/discovery.service.ts` (orchestration logic that uses those primitives) — keeps the highest-risk, most-iterated-on code isolated.
- `compiler.service.ts` is separate from `execution.service.ts` so self-healing can plug into execution later without touching the compiler.
- Zod `schemas/` (API input validation) is kept visually distinct from Drizzle `db/schema.ts` (database tables) despite the naming similarity.

## 4. Database Schema (Drizzle, pushed to Neon)

Three core tables — deliberately minimal for MVP (no users, no auth, no versioning):

```typescript
export const workflows = pgTable("workflows", {
  id: uuid("id").defaultRandom().primaryKey(),
  name: text("name").notNull(),
  targetUrl: text("target_url").notNull(),
  taskDescription: text("task_description").notNull(),
  workflowGraph: jsonb("workflow_graph").notNull(), // discovered steps/nodes
  createdAt: timestamp("created_at").defaultNow().notNull(),
});

export const runs = pgTable("runs", {
  id: uuid("id").defaultRandom().primaryKey(),
  workflowId: uuid("workflow_id").notNull().references(() => workflows.id),
  status: varchar("status", { length: 20 }).notNull().default("pending"), // pending | running | success | failed
  inputValues: jsonb("input_values"), // e.g. { query: "laptops", maxPrice: 800 }
  startedAt: timestamp("started_at").defaultNow().notNull(),
  completedAt: timestamp("completed_at"),
});

export const results = pgTable("results", {
  id: uuid("id").defaultRandom().primaryKey(),
  runId: uuid("run_id").notNull().references(() => runs.id),
  data: jsonb("data").notNull(), // extracted structured output
  createdAt: timestamp("created_at").defaultNow().notNull(),
});
```

Status: schema written, migration generated (`0000_warm_captain_cross.sql`), pushed to Neon successfully — confirmed working end to end.

## 5. Workflow Representation

A workflow is a graph of action nodes. Actions are parameterized (values supplied at runtime, not hardcoded), so the same workflow shape can be re-run with different inputs:

```json
{
  "steps": [
    { "action": "navigate", "url": "..." },
    { "action": "search", "value": "{{query}}" },
    { "action": "filter", "field": "price", "value": "{{maxPrice}}" },
    { "action": "extract", "fields": ["name", "price", "url"] }
  ]
}
```

MVP scope: linear workflows only. LOOP / CONDITION / LOGIN_CHECKPOINT node types and structural adaptation to a changed task are out of scope for MVP (see PRD section 6).

## 6. API Design (planned)

| Method | Route | Purpose |
|---|---|---|
| GET | `/health` | Uptime check — implemented |
| POST | `/workflows` | Create a workflow: runs discovery against a URL + task, saves the resulting graph |
| GET | `/workflows` | List saved workflows |
| GET | `/workflows/:id` | Get one workflow's details/graph |
| POST | `/workflows/:id/run` | Execute a saved workflow, optionally with new input values |
| GET | `/runs/:id` | Get a run's status and results |

## 7. Core Engine Responsibilities

- **`automation/browser.ts`** — manages Playwright browser/context lifecycle. Headless toggled by `NODE_ENV` (visible in development, headless in production) for easier local debugging.
- **`automation/discover.ts`** — identifies relevant page elements (search box, filters, product cards) using DOM/accessibility information; matches task intent to elements, falling back to an LLM only for ambiguous cases (deterministic-first, AI-assisted where needed, per PRD differentiation strategy).
- **`services/discovery.service.ts`** — orchestrates a full discovery run: opens the target, performs the task once to observe the sequence, records it as a workflow graph.
- **`services/compiler.service.ts`** — converts a workflow graph into executable Playwright steps.
- **`services/execution.service.ts`** — runs the compiled steps, collects results, writes to `results` table / Apify Dataset.
- **`services/apify.service.ts`** — calls the Apify API to trigger Actor runs and (stretch) manage Schedules.

## 8. Self-Healing Flow (stretch)

```
Step execution fails (selector not found)
   → Inspect current page state
   → Find candidate replacement elements
   → Compare semantically (LLM-assisted where deterministic matching is insufficient)
   → Validate candidate
   → If confidence high: update workflow, continue execution
   → If confidence low: flag "needs review" rather than guessing
```

## 9. Apify Integration

- **Actor runtime (Apify SDK)** — the entire engine runs inside `Actor.main()`; this is the deployable unit, not a wrapper around it.
- **Dataset** — structured results from each run.
- **Key-Value Store** — persisted workflow definitions for replay.
- **Schedules** (stretch) — native cron-based triggering for recurring/monitoring runs, no custom scheduler built.
- **Proxy** (stretch) — anti-bot handling during automation.
- **Webhooks** (stretch) — notify on scheduled run completion / meaningful change detected.
- Not using any pre-built Store Actor (e.g. existing scrapers) — the discovery step is the core of what's being built, so relying on someone else's pre-built scraper would undercut the project's actual technical contribution.

Cost note: Apify bills compute in CUs (1 CU = 1GB RAM for 1 hour, ~$0.13–0.20/CU depending on plan) for Pay-Per-Usage Actors. Browser automation runs cost meaningfully more per run than lightweight HTTP-based checks. Monitoring/scheduled features should default to lower-frequency checks (hourly, not every few minutes) and use Playwright request interception (block images/fonts/unneeded scripts) to reduce per-run compute cost.

### Pay-Per-Event (PPE) Monetization — required, not optional

The hackathon requires the Actor to implement PPE monetization, not just plan for it. Implementation notes:

- Monetization must first be configured in the **Apify Console** for the Actor (sets up which event names are chargeable and their prices).
- In code, charge events using the Apify SDK:
  ```javascript
  import { Actor } from 'apify';
  await Actor.init();
  await Actor.charge({ eventName: 'discovery_completed' });
  // ... later in the run
  await Actor.charge({ eventName: 'workflow_run' });
  ```
  (Python equivalent: `await Actor.charge(event_name='discovery_completed')` inside `async with Actor:`)
- With PPE, there is **no separate platform-usage charge on top of event prices for the end user** — the event price is the full cost to them. This differs from the Pay-Per-Usage/CU model discussed above, which is for Actors NOT using PPE.
- Developer receives 80% of revenue from charged events; Apify keeps 20%. Profit = (0.8 × revenue) − platform costs — event prices must be set above actual compute cost per event, not just at cost.
- See PRD section 5a for the proposed event list (`discovery_completed`, `workflow_run`, `repair_performed`) and pricing rationale.
- Implementation is low-effort relative to core engine work (a Console configuration step + a few `Actor.charge()` calls placed at the right points in the execution flow) — but it is a hard requirement, so it must not be left out of the build plan or treated as truly optional polish.

## 13. Known Risks

- Anti-bot protection on real target sites (Temu, flight booking sites) may block Playwright outright — needs early testing (day 1–2), before committing further build time to a specific site.
- Skill gap: backend owner (Becca) is not deeply familiar with Playwright specifically — team should confirm early whether the Python-familiar data engineer takes ownership of the discovery/automation layer instead, to reduce risk on the hardest technical piece.
- Running headless browser automation inside an Apify Actor has its own resource/timeout constraints, separate from local Playwright behavior — should be checked against Apify docs before assuming parity.
- Five separate infrastructure pieces (Neon, Drizzle, Express, Next.js, Playwright, Apify SDK) — integration/config mismatches between local dev and the Apify Actor runtime are a common source of late-stage delay; getting a minimal Actor deployed and running on the Apify platform early (not left until the end) reduces this risk.
